# Rubric: is this PR ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-matches-plan | The set of files and changes in the diff, compared against the plan-context block's scope statement, its not-in-scope line, its named files, and its recorded deviation notes; then the PR description's own claims about fidelity read against the same diff. Live: `git diff main...HEAD` against `plan.md` including its `## Deviations` section. | **The diff delivers the plan's work and only the plan's work, except where a difference is recorded in writing.** A difference is recorded when the plan's deviation note names it **or** the description states it plainly as a limit, a deferral, or an addition; a deviation carried in both is the strongest form and the one to look for. **Fail** if any of: (a) **the diff does more than the plan** — it changes a file the plan never names, adds a user-facing flag, option, or setting, renames or restructures code, or reworks an adjacent behavior, and no deviation note or description sentence accounts for it. A plan that says "Not in scope: new flags" against a diff adding one is this failure in its clearest form; (b) **the diff does less than the plan** while the description claims otherwise — the plan promised two deliverables and one is absent, or the description says a thing is now documented, handled, or fixed when no hunk does it. Claiming more than the diff delivers is drift in the shrinking direction and fails the same way; (c) **the description asserts a fidelity the diff contradicts** — "implements the plan exactly", "no changes beyond the plan", "no functional changes outside X" — while an unaccounted hunk sits in the diff. Treat such a sentence as a claim to verify, not as evidence. A deliberately scoped-down PR whose shortfall is recorded in the plan and restated in the description **passes**: the disclosed shortfall is the honest case this check is built to protect. **Two limits on what counts as "more than the plan".** First, the unit of comparison is **the change the plan specified, not every downstream consequence of it**: when the plan specifies a change to a function, module, or file it names, the effect that change necessarily has on the other callers of that same named code is **planned work**, not drift — a plan saying "function F returns an aggregated error when every target failed" authorizes F returning that error to every caller of F, unless the plan states that a particular caller must be insulated from it. Grade the hunks against the plan's specified change; do not treat a ripple inside the named code as an unannounced addition, and do not read a description's shorthand summary of a deferral as a promise that no behavior anywhere else moved. Second, work the plan **names as support** for its change — its test, its fixture, its changelog entry — is planned even when the plan did not enumerate the file. Drift is a change to code the plan never specified and no note accounts for, which is a different thing from a consequence of the change it did specify. | required |
| evidence-decisive | The PR's test-evidence block, read against the plan's test plan and against the specific lines the diff changes; plus the repo-facts block's stated checks (its test, lint, or format commands, or the PR template's "tests added and passed" ask) read against whether the evidence shows them run. | **The evidence shows the changed behavior actually changing, on the path the diff touches.** Both must hold: (1) at least one **observable before/after** — the plan's reproduction re-run with the failing result and then the fixed result, or a new test with its assertion named and its outcome shown — where the two differ in a way a reader can check; and (2) the **repo's own stated checks appear run with their outcome visible** when the repo asks for them. **Fail** if any of: (a) the evidence is an **assertion of success with nothing named** — "tested locally and it works now", "verified working on my machine for a full day", "all tests pass" with no test, command, or result identified; (b) the evidence **exercises a path the diff did not change** — the control case that never failed, a related-but-different input, a flag combination other than the one the issue reports — so the shown success is not about the fix; (c) the plan's test plan named **more than one failure mode and the evidence covers only some of them** without saying which are untested; (d) the repo's stated checks are **never shown** and the PR offers no outcome for them. A terse artifact that shows the symptom flipping passes; a long narrative of diligence with no shown result does not. | required |
| diff-reviewable | Every hunk in the diff, read for content that is not part of the change: debug output, commented-out code, unreachable or unused code, formatting-only edits, import reshuffles, and hunks in files unrelated to the fix. The commit list as corroboration only. | **A reviewer can read the diff and see only the change.** **Fail** if the diff carries any of: (a) **debug instrumentation left in** — a `print`, `eprintln`, `console.log`, `DEBUG` line, or temporary logging added by this branch; (b) **commented-out code** — a disabled earlier attempt, a commented debug line, or an experiment left in place; (c) **dead code** — an unused function, an unreferenced variable, or a body kept alive only by an `allow(dead_code)`-style suppression the branch added; (d) **churn** — hunks that only re-indent, re-wrap, reorder imports, or re-print identical lines, where the before and after are semantically the same; (e) **unrelated hunks** — edits to files or regions with no bearing on this fix, folded into the same diff. Judge the diff's content, not the commit messages: vague commits like `wip`, `fix`, or `misc cleanups while debugging` are corroboration that debris may be present and are a reason to read every hunk closely, but they are **never the fail on their own** — a clean diff under terse commit messages passes. Tests, fixtures, changelog entries, and documentation the plan called for are part of the change, not debris. | required |
| standards-met | The repo-facts block's two standards lines — `pull requests:` (the PR template's asks and any required checklist) and `contribution policy:` (the contribution guide and any AI policy) — read against the PR's title, description, and diff. Live: the repo's PR template, CONTRIBUTING, and AI policy files against the draft title and description. | **Both limbs must hold.** **(a) Template and stated asks.** Where the repo states a PR template or contribution asks, the PR satisfies them: the sections the template requires are present and answered rather than left as headings or deleted; a required issue link (`closes #xxxx`, `fixes #<n>`) is present when asked for; a required checklist is filled rather than absent; and where the ask names an **artifact in the diff** — a changelog entry, a whatsnew note, a regenerated cheatsheet — that artifact appears in the diff. **Fail** when a stated requirement is visibly unmet: a required checklist absent, a required issue link missing, a named changelog or whatsnew file never added. A repo with **no PR template and no stated asks owes nothing here** and passes limb (a). Do not invent asks the repo-facts block does not state, and do not fail a PR for omitting a section its repo never asked for. **(b) AI-use disclosure.** Treat the package as **AI-assisted work, because it is**; a stated disclosure duty therefore always applies. If the policy **requires disclosing AI assistance** — in any form, anywhere, or in pull requests specifically — the description must state that AI assistance was used and in what way. A policy that states **no AI rule**, that asks only for **responsibility, understanding, or testing**, that requires the work be in the contributor's **own words** (an own-words clause is not a disclosure clause), or that **explicitly exempts** this artifact from its disclosure ask, passes limb (b) automatically. **Fail** limb (b) when a stated disclosure duty is unmet — most importantly, a repo requiring disclosure of all AI usage and a description that never discloses, however good the fix and its evidence are. | required |
| thread-engaged | The `## Thread highlights` section and the issue body for maintainer direction or open questions — a maintainer naming an approach, setting a constraint, authoring a diagnosis, or asking something the fix answers — read against what the PR description says about it. | The description **engages the direction or question the thread raised**: implements it and says so, answers the question the maintainer asked, or explains why it went another way. Where the thread carries no maintainer direction and no open question, this check passes with nothing owed. | preferred |
| regression-guard | The diff's test files and fixtures, read against the defect the issue reports. | The diff adds or updates a test that **would fail without this fix** — a regression case covering the reported defect, not only a general smoke test — and the plan's intent for it is visible in the diff rather than promised in prose. A PR that is honestly scoped as untestable in the current harness, and says so, passes with nothing owed. | preferred |

## Verdict rule

**Accept** if every `required` check is `pass`. **Reject** if any `required` check is `fail`. An `unclear` grade on a required check counts as **fail**: a PR whose readiness cannot be established from the package is a PR that is not ready to submit. Keep the `unclear` grade in the output rather than rewriting it to `fail`, so the cause reads as absence of evidence rather than a failed condition.

The two `preferred` checks (`thread-engaged`, `regression-guard`) **never change the verdict** in either direction. They separate a strong submission from a bare one, and a package can be accepted without either.

Both limbs of `standards-met` must pass for that check to pass; a failure of either limb fails the check and holds the package. When any check fails, its evidence line names the specific sub-condition or limb that decided it, in this rubric's own terms.
