# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The environment record in the repro report (the "Environment:" line, block, or table, wherever the report states what it ran on), read against the version and conditions the issue itself states, and against the environment facts the repo's bug-report template asks for in the repo-facts block. | The report states **both** of the following as facts about the run: (1) the **version or build of the software under test** — a release number, a package/commit identifier, or a named build (a bare "latest" is not a version); and (2) the **platform it ran on** — the OS (with version), or the runtime that stands in for it when that is what the software runs inside (browser and version, playground, container image). Additionally, (3) when the issue or its thread states that the behavior **depends on a specific axis** — an OS-specific bug, a driver or backend, a shell, a build profile (debug vs release), a language or locale setting — the report must state its value on that axis. **Fail** if the report carries no environment record at all, or names only a product version with no platform, or omits an axis the issue says the behavior turns on. A report that describes hardware ("RTX 4080, 64 GB RAM") but never states the software version and OS still fails. | required |
| steps-rerunnable | The reproduction steps in the repro report, read as a stranger with a clean machine and no access to the author's disk would read them, together with the inputs those steps name (file contents, config, commands, links). | Every step needed to get from a **clean starting state to the trigger** is present as a concrete action the reader could perform, and **every input the trigger needs is either given inline in the package or publicly obtainable** (quoted file contents, a command that creates the input, a public URL, or an explicit "the exact N lines from the issue"). **Fail** if any of the following is true: (a) a decisive input is **unobtainable by the reader** — a private repository, an internal config file, a company monorepo, an unshared dataset, a screenshot described but not shown in place of the artifact; (b) a step is a **summary standing in for the action** ("set up the project", "configured it as usual", "ran our pre-commit hook") where the action itself is what the reader must perform; (c) a **parameter the issue says the behavior depends on is never named** in the steps, so following them lands the reader somewhere else (for example running the tool with its default backend on an issue whose steps specify a particular driver); (d) there are **no steps at all**, only an assertion that the behavior occurs. | required |
| artifact-shows-issue-behavior | The artifacts in the repro report (command output, log excerpts, error text, exit status, rendered output, screenshots) read line by line against the **specific** behavior the issue describes: its error message, its exit condition, its crash, or its named wrong output. | **Pass** if **either** of these holds. (A) **Reproduced**: at least one artifact in the report exhibits the issue's described symptom — the same error or panic text, the same exit condition, or the same observably wrong output — and what the artifact shows agrees with what the report says it shows. (B) **Honest cannot-reproduce**: the report states plainly that the behavior did **not** occur, and shows the artifact of the real attempt (the actual output of running the trigger, demonstrating the non-occurrence). **Fail** if: (a) there is **no artifact at all**, only narration ("can confirm", "I verified this", "it happens every time"); (b) the artifacts only show that the tool **ran or was installed** — a version banner, a session list, a successful startup, the environment being prepared — and nothing shows the reported symptom; (c) the artifact shows a **different failure than the one reported** and the report narrates it as the reported one, for example a graceful argument-validation error or usage message presented as a crash, a compile or syntax error presented as a runtime failure, or output that scrolled while the process stayed alive presented as a process crash; (d) the report's own **"expected" and "actual" contradict its artifact** or are stated backwards from what the artifact shows. Judge what the artifact contains, never how well the report is formatted: a terse artifact that shows the symptom passes and a polished report whose artifact shows something else fails. | required |
| target-configuration-faithful | The configuration the report says it ran (from its environment record and steps) compared against the versions and conditions the **issue and its thread** say the behavior occurs on, plus any difference the report itself names and what it says the difference means. | **Pass** if **either** (1) the recorded configuration is one the issue or thread **implicates** — the version the issue targets, a later release of the same line, or the platform the issue names when the issue is platform-specific; **or** (2) the report **explicitly names the difference** between what it ran and what the issue targets, and says what that difference means for its result ("filed against 13.0.0, unchanged on 15.2.0", "the report is macOS + fish, mine is Linux + zsh, which is likely why I could not trigger it"). **Fail** if: (a) the report ran a configuration the issue does **not** implicate — most often an **older version than the one the issue confirms the bug on** — and never names the deviation, so the shown behavior is that other configuration's behavior rather than evidence about the report; (b) the report **generalizes its result to a configuration it never ran**, or asserts its result holds on a build or channel the maintainers have said they could not reproduce on, without having run that one. Treat an unnamed deviation as failing even when the artifact looks like the reported symptom: a silent deviation is the failure. | required |
| claim-specific-and-honest | The candidate claim comment, read against the issue's own content (its symptom, error text, named file or function, and any pointer a maintainer left in the thread) and against what the rest of the package actually shows. | **All three** must hold. (1) **Specific**: the claim refers to something that belongs to *this* issue — its symptom, its error text, its file or function, its version, or a specific pointer from the thread — so it could not be pasted onto an unrelated issue unchanged. Generic enthusiasm ("great project, I love it", "this looks like a good one for me", "+1, any updates?") does not count. (2) **Honest intent**: the next step it states is something the author controls — investigate, test, read a named code path, report back — and it promises **no fix, no merge, and no delivery date**. "I will fix it within 2 days guaranteed" fails; "kindly assign it to me" with no stated intent fails; asking to be assigned *alongside* a concrete stated next step does not fail on its own. (3) **No overclaim**: the claim asserts nothing the package does not show. If the claim says the behavior was reproduced or confirmed, the repro report's artifact must actually show it (check `artifact-shows-issue-behavior` case A); if the claim names a version, channel, or platform as confirmed, the report must have run it. On a claim-only draft, a claim that **promises** a forthcoming reproduction passes, and one that **asserts** a reproduction not yet posted fails. | required |
| conventions-and-disclosure | The "contribution policy" line and the "bug reports" template line in the repo-facts block (live mode: the repo's CONTRIBUTING, AI policy file, and issue template), read against what the claim comment and the repro report actually say. | Treat the package as **AI-assisted work**, because it is; so a stated disclosure duty always applies. **Pass** if every stated rule that bears on these comments is satisfied: (a) if the policy **requires disclosing AI assistance** — in any form, anywhere, or in comments specifically — then at least one of the two comments **states that AI assistance was used and in what way**; (b) if the policy requires that comments to maintainers be **the contributor's own words** rather than machine-generated text, the comments read as one person's specific account of their own run rather than interchangeable template prose; (c) if the policy **bans** the kind of contribution the package proposes, the package does not proceed as though it were permitted. A policy that states **no AI rule at all**, or that only asks for responsibility, understanding, or testing **without a disclosure ask**, passes (a) automatically — silence is not a duty, and a responsibility clause is not a disclosure clause. A policy that explicitly says there is **no disclosure ask for issue comments** also passes (a). **Fail** when a stated duty above is unmet: most importantly, a repo whose policy requires disclosing all AI usage, and comments that never disclose. | required |
| control-or-contrast-run | The repro report's artifacts, looking for a second run placed next to the failing one. | The report includes a **control or contrast run** that isolates the trigger — the same command with the triggering condition removed, a neighbouring input that behaves correctly, or the shifted-away-from-the-boundary case — and shows its output too, so the reader can see the difference rather than take it on faith. | preferred |
| next-step-grounded | The claim comment's stated next step, read against the issue body and the thread highlights. | The next step is **anchored in something already on the issue** — a code path a maintainer pointed at, a linked upstream issue or PR, a draft patch in the issue body, or a suggested test — rather than a generic intention to start looking. | preferred |

## Verdict rule

**Accept** if every `required` check is `pass`. **Reject** if any `required` check is `fail`. An `unclear` grade on a required check counts as **fail**: proof I cannot verify is proof that is not ready to post upstream.

The two `preferred` checks (`control-or-contrast-run`, `next-step-grounded`) **never change the verdict** in either direction. They describe what makes a passing package stronger, and a package can be accepted without either.

**Claim-only drafts (live mode).** When the package is a claim comment with no repro report yet, the four checks whose evidence is the repro report — `env-recorded`, `steps-rerunnable`, `artifact-shows-issue-behavior`, `target-configuration-faithful` — and the preferred `control-or-contrast-run` are reported `unclear` with evidence `not yet applicable: claim-only draft`, and are **excluded from the verdict**. The verdict then rests on `claim-specific-and-honest` and `conventions-and-disclosure`, and answers only: is this claim comment ready to post? Eval mode never uses this branch; it always grades the full package.
