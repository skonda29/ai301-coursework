# Rubric: is this a good first issue?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| repo-not-archived | The "archived:" field in the repo-facts block (eval mode) or the repository banner on github.com (live mode). | The repo is **not** archived. An archived repository is read-only; no pull request can be merged. If `archived: true`, fail. | required |
| maintainer-active | The "last 5 default-branch commits" list in the repo-facts block. For each commit, note the author name and the commit date. Ignore any commit whose author name ends in `[bot]` — a bot commit alone is not evidence of human maintainer life. | At least **1 human-authored commit** (author name does not end in `[bot]`) on the default branch is dated within **365 days** of the capture date (eval mode) or within 365 days of today (live mode). | required |
| scope-bounded | The issue title, body, and the full Comments section in the bundle. | The issue describes a **single, bounded piece of work** a newcomer can finish in one pull request. A single task that naturally touches multiple files or lists several implementation steps is still bounded — what matters is whether one person can complete it in one PR. **Fail** if any of the following is true: (a) the issue is explicitly an **umbrella, tracking, or mega-issue** designed for multiple contributors to each take a separate sub-task independently — for example, "incrementally add type annotations across the codebase" where each module is a separate contribution, or a tracking list of many separate items each meant as its own PR. Keywords like "megaissue" or "tracking issue" in the title or body are strong signals. A single coherent task such as "document feature X" or "fix bug Y" that describes implementation steps or touches several related files is NOT an umbrella — it is one bounded task with a plan; (b) the issue is a **bare feature wish or unvalidated product proposal** — it proposes a new capability in only a few sentences, the feature requires a **product or design decision** the project has not already committed to (e.g., "add a company logo to the toolbar" for a generic tool, or "change the default behavior of X"), AND no maintainer, collaborator, or member has opened the issue or endorsed it in comments. A bug report, a documentation task for existing functionality, or a detailed proposal with clear acceptance criteria is not a bare feature wish even if no maintainer has responded; (c) the comment thread shows **unresolved design debate lasting more than 90 days** with no maintainer settling on a direction — the work cannot start because the spec is not decided; (d) the issue has **2 or more closed-but-unmerged linked PRs** AND has been open for **more than 365 days** — repeated abandoned attempts signal hidden difficulty beyond a first issue; (e) the issue is a **support or usage question** ("how do I…"), not a request for a code or documentation change. | required |
| not-claimed | The "this issue: assignees:" field, the "linked PRs:" field (with open/closed/merged state for each), and the Comments section in the bundle. | **All three** of the following must hold: (1) **No assignee** is currently listed. (2) **No linked PR is currently open** (a closed-unmerged PR is an abandoned attempt and does not block; a merged PR does not block). (3) **No active claim comment** exists — defined as a comment within **180 days** of the capture date where someone states they are working on the issue ("I'll take this," "working on this," "can I work on this") AND that claim has not been released (by a maintainer removing assignment, by a bot auto-unassignment message, or by the claimant saying they are dropping it) AND is not contradicted by a maintainer explicitly inviting new takers. A claim older than 180 days with no follow-up PR or activity is stale and does not block. A maintainer or collaborator explicitly stating that a specific contributor's PR is the only one accepted counts as an active claim regardless of the 180-day window. | required |
| ai-contribution-allowed | The "contribution policy" line in the repo-facts block. Look for any statement about AI, generative AI, LLMs, or machine-generated code in the contribution guidelines. | The repository does **not** contain an **outright ban** on AI-generated contributions. An outright ban uses language like "we do not accept AI-generated code" or "AI-generated PRs will be closed." **Fail** if such a ban is present. **Pass** if the policy sets conditions on AI use (disclosure, personal review, testing requirements) — conditions are terms to follow, not bans. **Pass** if no AI policy is stated (silence is not a restriction). | required |
| good-first-issue-label | The issue labels listed in the bundle header or on the issue page. | The issue carries a label signaling newcomer-friendliness: `good first issue`, `Good first issue`, `Easy to Fix`, `easy`, `help wanted`, or a similar variant. | preferred |
| maintainer-engaged | The issue opener's `author_association` field and the Comments section (check each commenter's `author_association`). | The issue was **opened by** someone with an association of OWNER, MEMBER, or COLLABORATOR, **or** at least one comment in the thread is from someone with one of those associations. | preferred |

## Verdict rule

**Accept** if every required check passes. **Reject** if any required check fails. Preferred checks (`good-first-issue-label`, `maintainer-engaged`) never change the verdict; they are used only to rank accepted issues by desirability. An `unclear` grade on any required check counts as **fail** — a first issue you cannot verify is not a first issue you should take.
